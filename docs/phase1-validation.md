## 二、自动化验证现状(截至本文件)

### 单元测试 — 172 个全绿

| 包 | 文件 | 覆盖 |
|---|---|---|
| shared | protocol.test.ts | 协议消息形状(类型级契约) |
| server | beatClock / room / roomManager | 权威节拍时钟、房间中继、NTP 应答、多房间创建/加入/回收、**新成员回填已有名单** |
| client | sync(clockOffset/beatGrid)、audio(scheduler)、input(keyboard)、guide(solfege/judge/guideEngine/barBoundary)、songs | 时钟偏移、节拍网格、调度器、双八度键位 + 鼓垫键位、判定窗口、引导窗口、曲库数据完整性(含摇滚三声部) |

### E2E — 5 个场景全绿(`npm run e2e -w client`)

1. **two browsers**: A 创建房间 → B 凭码加入 → 花名册互见 → 双向音符传输(中位 5ms)→ 读数稳定
2. **room error**: 加入不存在的房间 → 错误提示 → 回到 OFFLINE 可重试
3. **song guide**: 选摇滚曲目 → 武装鼓声部 → 倒计时 → 鼓垫引导高亮 → 判定命中 ≥ 1
4. **tempo/meter broadcast**: A 改 BPM/拍号 → B 实时跟随
5. **four players**: 4 人同房间花名册互见 + 音符扇出到所有人

### 环境注意

- ws 服务器 E2E 用 8081(本机 8080 被无关守护进程占用),见 `client/playwright.config.ts` 注释
- smplr CDN 在本机不可达,E2E abort CDN 请求使振荡器降级立即就绪(真实环境应能加载采样音色)

## 三、待人工验证的验收(执行协议)

### 协议 A — 4 人真实设备局域网合奏

1. 一台机器跑 `npm run dev:server`(局域网 IP 的 8080 端口);每台设备打开 `http://<服务器IP>:5173`
2. 房主「创建房间」拿到 6 位房间码;其余 3 人填码「加入房间」
3. 选《摇滚循环 Rock Groove》,四人分别武装 鼓/贝斯/键盘 ×2(或按实际人数分配声部)
4. 倒计时结束后合奏一首完整循环;逐台确认:
   - 节拍对齐听感无错位(参照: 120 BPM 下 1/32 音符 ≈ 15ms)
   - 鼓手/贝斯手/键盘手在每台设备上听到各自的音色(按发送者乐器回放)
   - 声部音量混音滑块各自独立生效
5. 记录: 设备数、系统(Chrome/Edge/Safari)、任何对齐漂移或掉音现象

### 协议 B — 新手 5 分钟上手计时

1. 招募 1 名完全不懂音乐的测试者(不透露操作细节)
2. 让 TA 从打开页面开始,口头说明「和朋友一起合奏,你选一个最简单的声部」
3. 计时到「第一次完整跟完自己的声部(不中断)」;记录:
   - 到达该状态的时间(目标 < 5 分钟)
   - 过程中遇到的困惑点(引导是否看懂、键位是否找得到)
4. 观察引导模式: 下落音符 vs 乐器高亮,TA 更喜欢哪个、哪个更易上手

### 协议 C — 定性访谈(≥ 8 人)

半结构化提纲(每人 15–20 分钟):
1. 你之前玩过乐器/音游吗?接触音乐软件的经历?
2. 引导(下落音符/乐器高亮)你看懂了吗?哪个更直观?
3. 和朋友合奏时,「听到大家一起把曲子合起来」的感觉如何?
4. 你觉得什么地方会劝退新手?什么地方让你想再来一次?
5. 如果让你推荐给朋友,你会怎么介绍它?
6. 付费/持续使用意愿(仅供产品方向参考)

产出: 每场访谈 3–5 条要点 + 共同主题归纳;用于验证「引导式合奏是否真的让新手感到乐趣并愿意再来」。

## 五、发现并修复的产品 bug(本报告周期)

1. **新成员看不到已有成员** — room.join 缺少名单回填,后加入者花名册为空。已修复 + 单测锁定。
2. **倒计时竞态** — 声部武装发生在第一条时钟广播之前时,倒计时锚点取 0 拍,导致倒计时立即过期、整首歌被跳过。已修复(latestBeat 未知时挂起武装,收到时钟后补启动倒计时)+ E2E 覆盖。
3. **React 受控 range 输入** — E2E 手动派发 input/change 不触发 onChange,改为真实键盘事件(记录供测试复用)。
